## 确认的现状与原因

- `local-app/public/app.js`的`profileField`为每项同时创建中文、英文和确认框；共享schema标签也有中英双语。
- `profile-file-import.js`为每项展示文件内容、原始依据、字段路径、当前值、目标下拉及处理下拉；当前确认API主要提交处理选择，尚不能把导入值直接编辑后保存。仅换布局不满足本次要求。
- `profile-update.mjs`根据最高学历的在读标记给学位和结束日期加`in_progress`；现有阻止规则可能把“硕士”整个留在待处理。纯内存虚构样例已复现学位未写入。
- 同一项目的`项目描述`、`职责`、`项目中职责`、`描述And职责`被明确拼接到一个`projects.<id>.description`；`role`没有对应导入值。虚构复现中四段在一个字段、角色为空。
- `selfDescription.专业技能`被固定映射到`skills.description`，已有编程/机器人与视觉/嵌入式/工具/硬件栏未分配。虚构复现中仅综合技能有值。
- 现有`model.mjs`的集中补答、持久保存和同任务重新inspect流程可复用。`greenhouse-adapter.js`在问题收集及提交前检查中以`required || alreadyPopulated`筛选，空白选填普通问题会被排除，不能承诺当前已经覆盖“所有未填问题”。原始`fields`存在不等于已形成平台待答清单；本轮需覆盖这项实际缺口。

## 必须实现

### 1. 中文单份资料，紧凑核对

- 从资料日常编辑和导入核对界面移除英文值输入栏、英文内容副本及中英双语字段标签。用户只维护一份中文资料；Python、C++、ROS等技术专名与邮箱/链接不是要删除的“英文栏”。兼容旧文件不能再要求用户填写第二套英文。
- 去掉默认逐项“原始依据/文件字段/内部ID/目标路径/来源说明”等展示，不把这些换成另一组长卡片。内部为恢复/校验保留必要信息即可；普通用户流程无需展开或阅读技术证据。
- 导入后直接显示与个人资料一致的可编辑草稿，按个人信息、教育、实习、项目、技能紧凑分区。正确值直接预填；有真实冲突/歧义时仅在相关字段附近给出简短选择，其他字段不重复确认。
- 只有一次整份核对保存动作，不再要求给每个普通字段另选接受、逐个勾确认，然后又到另一个表单保存。保存前草稿不作为可执行的确认资料；确认后可在同一资料页继续修改。
- 原已确认值、未保存编辑、版本变化和过期批次继续受保护。不得通过自动覆盖旧数据、自动授予提交许可或解除暂停来简化流程。新接口接受本人编辑的草稿值时保持服务端字段白名单、值校验和原子保存，不只是修改显示文本。

### 2. 硕士学位可读入，在读语义保留

- “硕士”是可表示的学位，不能因为该段仍在读就整项丢到待处理。草稿和保存后均应显示硕士，并在紧凑的学习状态或可无损表示的字段中保留在读含义。
- 在读/预计毕业与已毕业区分；不能把预计日期当成已经毕业，或通过删除限定来让检查通过。仅不确定的日期需待核对，不阻止学校、专业和学位这些已知内容。
- 此要求按结构与语义实现，不硬编码用户学校名称或当前日期。

### 3. 四项项目内容独立保存和编辑

- 旧JSON里的四个源字段分别承接：`项目描述`、`职责`、`项目中职责`、`描述And职责`。最后一项可用清楚的中文标签“描述与职责”，但四项仍有各自独立内容。
- 原文与段落完整保留，同一个项目内四项可以分别修改、保存、重载；不再全部拼进“项目描述”，不把四项误拆成四个项目，也不把长职责当本人角色。
- 共享schema、校验、编辑器、导入/导出和实际涉及的字段消费者保持一致；内部键由Engineer选择。旧`description`数据必须可继续读取，不能仅增加界面空框。
- **用户已明确指定本轮三个项目的本人角色均为“核心成员”。** 在这次资料草稿修复中按该已确认输入预填，仍经一次资料保存；通用解析器不得把所有人的所有缺角色项目默认编造成核心成员。可采用明确的批量设定并作用于当前选中项目，确保这三个项目一次处理，不让用户逐条重打。

### 4. 技能逐条提取并归到对应栏

- 将原“专业技能”内已有技能按条拆出，进入编程技能、机器人与视觉、嵌入式、工具、硬件等对应栏，允许逐条修改。不能仍把全文塞入“综合技能”而其余栏全空。
- 优先采用原明确分类/标签和可核实技术词；歧义项保留原文并就地待确认，只有真正不属于其他类别的内容进入综合项。原文技能与熟练程度不遗漏、不凭经验增加用户没提供的能力，不把同一项无意义地复制到每一栏。
- 用户不负责重写JSON或逐项搬运技能；合理的初次分类由程序生成草稿，本人可以修正。无需模型API或新增AI服务。

### 5. 已导入资料的保留与修复

- 必须覆盖“旧版本已经导入过”这一实际情况。保留记录稳定ID、后续人工修改、R1映射、资料/附件版本、答案、任务、扩展身份和提交账本，不清空资料库重建。
- 能从已有导入记录或旧组合字段中按明确源标签无损恢复四项时，生成同一记录的修复草稿；已有修改发生冲突时就地处理。确实缺失来源时保留旧内容，仅请求最小必要补充，不根据同名记录猜合并或把不确定拆分结果当事实。
- 再导入同一文件不重复新增教育/项目；已经人工改过的字段不被旧JSON悄悄覆盖。数据结构迁移与重载需有兼容路径；不得为四字段扩展破坏已验收R1。

### 6. 未填问题留在平台，回答确认后继续同一任务

- 在当前已适配站点范围内，记录实际申请表中适用、可见而未填的普通问题，包含空白选填问题，不仅收集必填。已有已确认且适用的资料直接复用，不重复问。系统隐藏字段、不可编辑展示内容不冒充用户问题；条件尚未触发的字段在实际出现时检查。
- 平台保存问题原文、实际选项、所属公司/岗位/任务、必要的结构版本与处理状态，给用户展示简短问题和答案输入。未答/待确认状态刷新或服务重启后仍存在；同一原题不无限新增重复待办。
- 用户在平台输入并点“确认保存并继续”（可沿用现有按钮）即完成普通补答。已确认答案进入平台持久数据，不另导出/导入JSON、不要求用户改文件、不要求工程师逐次写代码。已识别的稳定事实在本人确认的适用范围内维护个人资料；公司/岗位/原题限定答案保持对应范围。日常界面不要求逐题研究内部路径或复杂保存配置。
- 选填问题允许本人明确选择本次留空，记录该选择后继续；必填不能借留空跳过，未填写或未确认不能被标为完成。无法可靠识别的控件、选项或验证码仍应在平台留下具体人工处理事项和恢复入口，不静默忽略，也不编造可填写答案；凭据及验证码由本人在目标页处理，不进入资料库。
- 保存后沿用原任务ID、答案和已有执行进度重新检查并继续，不新建一份申请。若资料/附件版本或授权范围改变，只要求必要的本次申请再确认，已答内容保留、不让用户重填；这不变成再次上传JSON。用户显式暂停、账号不符或结构变化仍应清楚显示阻塞原因。
- 未解决问题在提交前仍可追溯。结果未知或已经越过提交边界时只核对，不因补答/重启再次提交。复用现有任务、答案、版本与提交保护，不另建平行补答系统或扩大招聘站适配。

4. 使用含明确分类及至少一项歧义的虚构技能输入，核对分类栏、逐条编辑、原文完整性和待核对项，不再全挤综合栏。
5. 重复导入、已确认值冲突、dirty草稿、过期批次、旧数据兼容只跑实际受影响定点；原附件不变、保存资料不触发投递。共享schema/字段消费者被改时补必要针对性检查，不把旧检查“没跑”说成“全部通过”。
6. 在同一受支持站点的虚构实际表单中放置一个未答必填、一个未答选填及一个已有可复用事实：平台只列真实缺项，原题/选项可见；重载后待答仍在；用户直接回答/明确留空并确认，答案保留且同任务继续，全程无JSON上传。新动态问题出现时再记录，不丢失既有答案。补答引发资料版本变化时只保留必要的申请确认，原附件/unknown/手动暂停保护仍有效。
