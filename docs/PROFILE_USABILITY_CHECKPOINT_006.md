## 已核实结果及其边界

| 场景 | 实际结果 | 接收范围 |
| --- | --- | --- |
| 正常 | POST到达1、有效接受1、确认导航1，submitted | 真实MV3内部回执session核对同tab/document、XHR File字节及对象摘要、完整正文摘要、HTTP200、页面收到Response后的确认导航和实际确认地址；限虚构站及历史原客户端函数 |

| 捕获后撤销最终授权 | POST到达0、接受0、确认0，unknown | 测试在第二次authorize调用触发真实后台task-pause，并由产品授权拒绝放行；只覆盖这条受管失效 |
| 接受并落盘后丢响应 | 重启前后均POST到达3、有效接受1、确认0，unknown | 页面处理器一次、一次requestfailed、三个连接同正文；真实浏览器重启、后台实例从盘重建、重新配对后确认/继续被拒，verify未增加到达。不是独立后台进程重启或真实站唯一受理证明 |

**三次到达必须保留。** `local-app/tests/fixtures/greenhouse-native-gate-fixture.mjs:139–150` 明确在已有岗位接受记录、正文摘要一致时跳过第二次创建记录；第一次接受实际写临时文件并rename落盘。因而“只接受一次”包含虚构服务端去重合约，不能归功于客户端账本或假定Greenhouse也如此。客户端账本能够证明的是受测重启/恢复路径没有新增主动提交，不能约束单次fetch中的全部网络重发。

**后台重启措辞需修正。** `local-app/tests/greenhouse-native-gate-browser.mjs:192–206` 关闭Chromium，关闭app/server后在同一Node进程 `createApp`。每次确实新建Store并从state.json读盘，未见模块级任务缓存，随后确认/继续返回400、verify仍unknown，扩展持久profile账本也保留。这是有效的持久状态重载证据；工程报告/测试标签中的“后台完整重启”应明确为实例重建，独立后台进程退出/重新启动另补一次定点。

**传输归因保持为推断。** [RFC9110的幂等与重试说明](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)及与本轮浏览器对应的[Chromium145重发条件](https://github.com/chromium/chromium/blob/145.0.7632.6/net/http/http_network_transaction.cc#L2038)说明单次调用不保证单次HTTP到达。日志的相同正文/不同连接/一次页面调用符合浏览器内部重发，但没有网络栈trace证明每一次的具体触发路径；后两个新连接也不能仅用“复用连接”分支解释。不得宣称精确根因或“三次为上限”，本轮管理决策不以继续追查每个网络事件为前置。
