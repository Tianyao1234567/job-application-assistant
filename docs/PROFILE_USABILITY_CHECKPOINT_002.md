先完成一个纵向小验证，再集成产品：

1. **取得并隔离真实待发内容。** 明确完整请求从哪里取得；不能假定DNR阻断后CDP仍能读到它。页面原生请求持续阻断，可信路径能单独发送；不能靠页面可重放的URL/请求头标记充当授权，也不能靠临时放开整个端点发送。
2. **核验完整请求与原站约束。** 原任务/岗位/页面、执行身份、资料/附件版本、本人授权、动态字段、精确上传对象一致，核验后发送内容不可被替换。验证原站会话、Origin、CSRF、CORS/CSP及实际所需权限；虚构服务要检查对应约束，不能删除校验或伪造字段凑通。虚构测试不能单独证明原站兼容，交付需说明与现有原站协议证据的对应及剩余限制。
3. **复用一次提交保护。** 沿用原任务、最终授权和持久提交账本；可信入口不能由任意页面消息调用。授权失效、内容不符或机制不可用时不发送；调试器/执行端断开等已识别失效场景不释放页面请求。实际已发出后丢失结果保持unknown，重启不重发，不清账本重试。
4. **同时接通可信回执。** 现有`greenhouse-receipts.js`要求原tabId并依赖原申请页进入confirmation，独立发送不自动满足该条件。小验证必须含可靠回执或只读核对；不能将HTTP 2xx直接记为submitted。

最小通过标准：正确完整请求只有可信路径到达1次并形成可信回执；错误附件/核验后换引用/缺失身份或CSRF/授权失效时收到0次；断开后页面请求仍为0；请求已发但丢失回执，重启后总数仍为1且任务unknown。记录实际服务接收数与产品状态，使用真实MV3及拟支持浏览器/权限，不以受控执行器代替。先证明这组关键条件，无需重跑不受影响的资料修复和补答场景。
